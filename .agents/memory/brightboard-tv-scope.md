name: BrightboardTV presenter product scope
description: Broad presenter audience, open-source boundaries, QR remote control and installation guidance
---

BrightboardTV is open-source interactive presentation software used directly
through Brightboardapp. Its audience includes teachers, public speakers, CEOs,
managers and anyone making interactive presentations. Preserve the footer link
called “BrightboardTV”, full open-source/installation/use documentation, and the
television icon with the letter B inside.

**Why:** The user explicitly broadened the audience beyond teachers and requested
phone/tablet control so people without smart screens can present from a distance.

**How to apply:** Include QR pairing and private presenter notes, not just a
static casting instruction. Distinguish synchronization of BrightboardTV content
from native screen/audio mirroring, which depends on device support. Keep 3D
exploration and whiteboard tools relevant to classroom and business presentations;
do not interpret TV as a streaming/video subscription service.

About Us, Features and the footer must explain this wider audience and that
others can use, modify and build on the open-source presentation core.

**Why:** The user explicitly requested these public-page updates, not just a
separate BrightboardTV download page. Keep the existing verified founder story.

**How to apply:** Keep public messaging consistent across these pages. Do not
reduce BrightboardTV to teachers only or imply the whole hosted website is
included in the independently licensed open-source distribution.

The public source distribution must have its own clean source boundary and no
history from BrightBoard's private application.

**Why:** The user wants open-source software, not public exposure of account,
payment, founder-dashboard or customer information.

**How to apply:** Export only the independent presentation core, its relay,
original/licensed assets and documentation. Never push the private root repository
or attach its history to the public project.

BrightboardTV software downloads need their own visible founder-only counter,
website history and GitHub release-download totals, separate from existing
generated-content reporting.

**Why:** The user explicitly limited this request to BrightboardTV software and
reiterated that the download counter was missing from the founder dashboard, and
then explicitly requested the GitHub download counter too.

**How to apply:** Keep the counter near the dashboard overview. Describe its
coverage honestly: hosted ZIP responses are measurable; external GitHub
downloads, clones, browser installation and successful disk saves are not the
same events. Do not invent historical totals or expose these owner statistics
on public pages.

Manual “Save to lesson library” on the BrightBoard-hosted version is for paid
users; free users must see a gray disabled save control and an explanation.
Downloads/exports remain available. Keep the independent open-source distribution
free of BrightBoard account or payment dependencies.

**Why:** The user explicitly requested paid-only, grayed-out library saving.
The existing open-source boundary still requires a usable independent core.

**How to apply:** Verify hosted entitlement through the server using the current
subscription, never infer payment from a client-side toggle. Distinguish manual
library saving from safety recovery backups so gating does not destroy work.

Use the compatibility/legacy PDF.js browser entry and its matching worker for
presentation imports, even when the modern bundle builds successfully.

**Why:** The default PDF.js bundle required Map.getOrInsertComputed in the
verification browser, causing every PDF import to fail despite a passing build.
Both the main browser module and the worker need the compatibility polyfills.

**How to apply:** Keep the main/worker versions paired and confirm PDF rendering
in a real browser after PDF.js upgrades; a successful build is not sufficient.

BrightBoard and BrightboardTV must be two separate installed apps. BrightBoard
is not open source; BrightboardTV is. Customer-facing BrightBoard authentication
screens and verification emails must retain BrightBoard branding rather than
AfroAI branding.

**Why:** The user explicitly requested separate installed apps and corrected the
provider branding appearing in the installed window and verification email.

**How to apply:** Preserve these product and branding boundaries when changing
installation, authentication, email templates, or downloadable distributions.
